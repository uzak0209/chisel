# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Chisel is an experimental TypeScript toolkit for growing an executable business specification from a closed data model, generated examples, and human-provided expectations. The workflow is fixed and sequential:

```
declare data and behavior
→ generate unanswered examples
→ let a human fill expected results
→ refine data and behavior
→ implement an executable model
→ check the model against the examples
```

Requires Node.js >= 26 (uses the built-in `Temporal` API — see `mise.toml` for the pinned version).

## Commands

```sh
npm run typecheck   # tsc --noEmit
npm test            # vitest run (see vitest.config.ts: test.include is test/**/*.test.ts)
npm run check        # typecheck + test
npm run coverage     # vitest run --coverage (v8 provider, src/** only)
npm run build        # tsc -p tsconfig.build.json -> dist/
npm run demo         # runs examples/progressive-demo/run.ts end-to-end
```

CI (`.github/workflows/check.yml`) runs `npm ci && npm run check` on push to `main` and on every pull request. `.github/workflows/preview.yml` builds every pull request and publishes it with [pkg.pr.new](https://pkg.pr.new) (versioned `0.0.0-preview-<sha>`), running `pkg-pr-new` from the lockfile (a devDependency) as its README asks of CI; the pkg.pr.new GitHub App, not the workflow's token, comments the install command on the pull request.

Run a single test file directly with vitest, e.g. `npx vitest run test/chisel.test.ts`. Tests use Vitest (`describe`/`it`/`expect` imported explicitly from `"vitest"`, no globals). `expect(...).toStrictEqual(...)` (not `toEqual`) is the standard equality assertion here — it distinguishes `{ note: undefined }` from `{}` the same way `node:assert.deepStrictEqual` did, which matters for the `optional()` invariant below.

Every named construct takes its name as the first argument — `behavior(name, {...})`, `spec(name, {...})`, `action(name, {...})`, `compose(name, [...])`, `external(behavior, reason)` aside. The public API is meant to be used as a namespace (`import * as c from "chisel"`), like zod's `z` and valibot's `v`: README, `examples/` and `generate`'s output write `c.variants(...)`, `c.action(...)`, `c.check(...)`; tests keep named imports. The four entry points are `check` (adequacy of a specification, what `chisel check` prints), `generate` (the rows no row stands in yet, `{ rows, notComposed }`, what `chisel generate` prints), `test` (the answered rows run against production code, returning the rows that disagree) and `perform` (run the model once on one input).

`src/cli.ts` defines its commands with [`@politty/zod`](https://www.npmjs.com/package/@politty/zod) (politty's zod flavor; argument schemas are zod, and the file argument carries its own missing message so it reads `Missing required argument <file>`) and exports the root command as `cli` (`chisel` with `check` / `generate` subcommands). Handlers print with `console.log` and signal failure by throwing — politty turns a thrown error into exit code 1 (`runMain` prints it as `Error: <message>` on stderr). There is no other exit code: `--strict` inadequacy, a spec file exporting nothing, an unknown subcommand, and a missing `<file>` all exit 1; bare `chisel` prints help and exits 0. A top-level `isRunAsScript()` guard (comparing `import.meta.url` against the `realpathSync`'d `process.argv[1]`, so it resolves correctly through the `dist/cli.js` bin symlink too) calls `runMain(cli)` only when the file is executed directly. `test/cli.test.ts` drives `cli` in-process with `runCommand(cli, argv, { captureLogs: true })` for nearly all cases (fast, fully covered by `npm run coverage`), reading handler output from `result.logs.entries` and failures from `result.exitCode` / `result.error`, and keeps exactly one `spawnSync` subprocess test to prove the shebang/`isRunAsScript`/`runMain` wiring itself works end-to-end — that one test's process boundary is the only part of `cli.ts` Vitest's V8 coverage can't see.

The CLI can load `.ts` spec files directly (via `tsx/esm/api`'s `tsImport`), no build step required:

```sh
npx tsx src/cli.ts check ./examples/order-cancellation.spec.ts
npx tsx src/cli.ts check ./examples/order-cancellation.spec.ts --strict
npx tsx src/cli.ts generate ./examples/order-cancellation.spec.ts
```

package.json also exposes these as `npm run example:check`, `npm run example:strict`, `npm run example:generate`. `check` reports state without failing by default; `--strict` exits 1 when examples are unanswered, variants are uncovered, the implementation is absent/pending, control policies are incomplete, or the implementation disagrees with an example.

## Architecture

Everything is exported through `src/index.ts`, except `runIsolated`, which needs Node and is the `chisel/isolated` entry (`src/isolated.ts`); there is no barrel re-exporting beyond that. Four modules, each building on the last:

1. **`src/schema.ts`** — the data layer. `Schema<T>` is the common interface (`parse`/`placeholder`). `placeholder(name?)` takes the name of the field it fills: `object` hands each key down, and `array`, `optional` and (in `src/partition.ts`, where `positionAt` carries the holding field's key down rather than reading it back from the path, since a key may hold `.` or `?`) record values pass it on to what they hold, so `string()` takes no label and writes `"<orderId>"`, or `"<string>"` where no field holds it; its parse issue is `Expected a string`. A record's placeholder holds one entry, `<key>` mapped to the value schema's placeholder, the way an array's holds one element, so a length invariant (the record's own or an enclosing object's) repeats it as `<key2>`, `<key3>`, … Primitives: `string`, `number`, `int`, `decimal(scale)` (a decimal.js `Decimal`, a runtime dependency, with at most `scale` digits after the point; `parse` recognises one by its methods through `isDecimal` in `src/rule.ts` rather than `instanceof`, so another copy of the library is read too, refuses anything else as `Expected a Decimal` and more digits as `Expected a Decimal with at most 2 decimal places`, and answers -0 as 0; `ordering` in `src/rule.ts` compares Decimals by `comparedTo`, exactly; `decimalUnits`/`decimalOfUnits` read one as a bigint of units of its last digit and back, and `decimalStep` steps to the next value of the grid strictly past a bound, so a bound off the grid steps onto it; its placeholder moves by `decimalStep`, which `satisfy` takes through `stepAt` for every term reading a decimal, its own rules and those an enclosing object or sum writes on it, so `decimal(2).gt(0.5).lt(1)` stands in with 0.51; `codegen` writes it as `new Decimal("…")` and `generate` then prints the decimal.js import beside chisel's), `boolean`, `enum` (exported as `enum` from `enumOf`, since a function may not be named `enum`; `c.enum(["a", "b"])` takes its values like zod's, and what each means as its second argument, `{ labels: { a: "…" } }` (kept as `labels`, left off when not given, and refused when it names a value the enum does not), refuses a repeated one, parses any other value as `Expected one of "a", "b"`, and stands in with the first value its invariants keep: `satisfy` takes, through the `stepAt` that `refinable` hands it, the values an enum field's own invariants keep, and a rule on it, its own or one an enclosing object or sum writes, chooses the first of them the rule keeps rather than stepping; its `length` draws no border and is listed as not read, since its few values are no range a row can step through), `instant` (Temporal.Instant), `date`/`time`/`datetime` (Temporal.PlainDate/PlainTime/PlainDateTime, built by one `plain` helper; `parse` refuses any other value as `Expected a Temporal.PlainDate` and so on, and ordering two temporal types against each other does not type-check), `literal`, `array`, `record`; any schema takes `.describe(text)`, as in zod: it is kept as `description` through `refine` and the shorthands, replaced by a later `describe`, and carried up by `.optional()`, so a field reads the same whether it may be left out, and nothing parsed or measured reads it; any schema becomes optional with the `.optional()` method (there is no free `optional` function; the method is typed through `this` so that `Schema<T>` stays covariant in `T`). Every schema takes `.refine(v => v.$gte(1))`: the callback receives a symbolic term (from `src/rule.ts`, a Proxy: a key reads the field of that name, `v.start`, as `run` reads the value, and a key with a `$` prefix is an operator, so no field can shadow one (a `$` key naming no operator, such as `$id`, still reads that field, while a field named like a term operator, such as `$length`, is left out of the term type because the key reads the operator); `$length()` measures, and on a string `$trim()`, `$lowercase()` and `$uppercase()` transform what is read, as the `String.prototype` methods do, leaving the value as it is: a term's `Measure` is `value` or `length` after the transforms written before a colon (`trim,lowercase:length`, built by `measureOf` and read back by `partsOfMeasure`), one string so that two terms read one coordinate exactly when their measures are equal and a check for `measure === "value"` never takes a transformed value for the value itself; `counts`, `measured` and `rewrite` read and write every measure, a transformed length drawing borders on `lengthCarrier` and composing rows by resizing the transformed string (or writing `_`s where resizing leaves whitespace that `trim` takes off; where a string field's own invariants refuse what is written and the measure trims, the leaf position's `writer` (and that of an optional holding the string, where a guard's points are written) pads it with spaces to the length it had or a length its invariants owe a row at, so `c.string().min(1)` stands at `length(trim($)) = 0` with `" "`), a transformed value stepping past a bound as the transforms read it (`transformedStringCarrier` in `src/partition.ts`, falling back to `""` below a bound and to a run of U+10FFFF above it where stepping reads back across it, as `"Ba"` steps down to `"B"`, which lowercases above `"Ba"`) and writing only a string the transforms read as the target (`readingAs` in `src/rule.ts`: the target itself where they leave it alone, or, since `"ẞ"` uppercases to itself and lowercases to `"ß"`, which uppercases to `"SS"`, the target with each `ß` written `ẞ`), so `generate` composes a point through `writeExactly` and names one it cannot write in `notComposed` instead of offering a row away from it; a value `readingAs` finds no string for is one nothing reads as (the carrier's `produces`), so a point placed exactly there is `no point` (`none: no value reads as "abc"`, through `unread` in `src/border.ts`) and `ordered` in `src/feasibility.ts` never holds an equality with it, an invariant `$lowercase().$eq("ABC")` admitting nothing (a `modelIssues` entry) and the arm of such a guard owing no row; a transformed value of an enum or a sum's discriminant is read off each of its values instead (`finiteReach` takes such a guard into the finite plan, and `placedConstraintOf` in `src/feasibility.ts` turns it into `!=` the values whose reading it refuses, for feasibility and `witnessesOf`), so `lowercase($.level) == "high"` then `$.level == "Low"` owes no row; and a `length` invariant such as `string().min(1)` bounds the length only and says nothing of a transformed one) and returns a `Rule` made with the term's operators `$lt`/`$lte`/`$gt`/`$gte`/`$eq`/`$ne` (and `$all`/`$any` over array elements; a number or decimal term also takes `$plus`/`$minus`, which build a `linear` term — `TermData` is `PositionTermData | LinearTermData`, the parts weighed by whole numbers plus a constant — read by `read` as their sum, absent when a part is, and written `$.乙 - $.丙` by `describeRule`; a reader that only one position can stand at, such as what a `match` selects or `$all` ranges over, takes it through `positionOf`, which refuses an expression, and every other reader uses `positionData` and treats an expression as unread: `normalize` and `boundTermPath` give `undefined`, feasibility reads one over integer or number positions as a linear form (below) and any other as an opaque step, the finite measures leave such a decision out, while `betweenExpression` in `src/guard-borders.ts`, reached from `walk` for a guard or ensures clause and from `invariantPairBordersOf` for an input invariant, draws the border of a comparison holding one on `differenceOf(rule)`, the left side less the right as one linear form, rendered `@case.甲 − @case.乙 + @case.丙`, when every part is an integer or number (a decimal part leaves it unread, under `measures.comparisons`), its `reads` naming every part, and composes a point by moving each part weighed by one in turn (`GuardBorder.sides`, tried as `side` by `generate` until the input takes the row, since an earlier part may be held to a bound of its own); `withoutPairRefusedPoints` leaves an expression's points as drawn), combined with the rule's own non-enumerable `$and`/`$or`/`$not`, which `parse` enforces and `placeholder` satisfies. `parse` lists one issue for every invariant the value breaks, in the order they were written (still only once the value's own fields parse, so a sum's invariants are read only of a case that parses). `refine(name, rule)` (and each shorthand with a leading name, `int().min(name, 1)`, told apart from `min(1)` since a bound is never a string) names an invariant, taking the name first as every named construct does: the name is a plain `name` property on the stored `Rule` (not a side table, since the CLI loads a spec in another module graph), set only when given, so an unnamed invariant and its issue read exactly as before; a broken named one is `{ path, message: "Invariant <name> violated: <condition>", invariant: <name> }`; `conjuncts` hands the name to each part of a conjunction and `stepInto` keeps it, so the borders it draws, and a position it leaves nothing at in `modelIssues`, read `invariant <name>: <condition>` (the label is added in `src/border.ts`, not by `describeRule`, whose text keys ways and obligations); a name one schema gives two invariants is refused (`Invariant <name> is declared more than once`). There are no free functions for these; `Condition` types the combinators. Numbers (`number`, `int`, `decimal`) and the temporal types (`instant`, `date`, `time`, `datetime`, with a bound of their own type) also take the shorthands `min`/`max`/`gt`/`lt`, and strings, arrays and records `min`/`max`/`length` (on the length); each desugars in `refinable` to the rule `refine` would take (`int().min(1)` is `refine(v => v.$gte(1))`, `array(x).min(1)` is `refine(v => v.$length().$gte(1))`), so borders are drawn alike. A comparison whose operand is absent (an optional field left out) holds. Inside `of.$all(each)`/`of.$any(each)` the element term is rooted at a name for the element (`#each<depth>`, by nesting depth so it reads the same in every module graph), and `holds` evaluates `each` against the enclosing scope with the element bound under that name (`bindElement`), so a term from outside the quantifier is read against the scope it was written in. `describeRule` and the guard analysis (`Frames` in `src/guard-borders.ts`) resolve an element name to the element's own scope, path and label, and everything else to the enclosing frame. Terms are tagged with `Symbol.for`, because the CLI loads spec files in a separate module graph. `object(shape)` composes fields and refuses a key its shape does not declare (`Unexpected key` at `$.<key>`; `variants` takes its discriminant off before handing the value to the case's object, unless that object declares the discriminant itself); `.optional()` fields become real `key?: T` in the inferred type (via `InferShape`), not a required `key: T | undefined`. `variants(discriminant, variants)` builds a tagged union over object variants and is central to the whole system: behaviors' `input` and `effects` must be `VariantsSchema` because coverage analysis is driven by enumerating `variantTags` — `array`/`optional`/`record` are only meant to appear *inside* an `object()` shape or as a behavior's `result` schema, never as a behavior's `input`/`effects` directly. `tagOf`/`isVariantsSchema` are the primitives everything else uses to identify which variant a runtime value belongs to.

2. **`src/behavior.ts`** — the behavior/implementation layer. `behavior(name, { description?, input, result, effects })` declares a boundary (data in, data out, side-effect vocabulary) without implementation. Its `description` says what it does and is left off the behavior when not given; a composition has none, and the result and effects sums `compose` builds for its joins carry no description of their own (each case keeps its object's). `implement(behaviorDef, { cases, controls })` supplies one action (or `todo(reason)`) per input variant, plus a `ControlTable` mapping each effect variant to a `ControlPolicy` (`execution: direct|outbox|queue`, `idempotency`, `compensation`, optional `exposure`) or `todo`. `perform` dispatches on the input's discriminant tag, runs the matching decision, and validates the input/result/effects against their schemas — throwing `SpecificationError` on any mismatch, missing case, or pending decision. A case is written as `action(id, { guards?, run })`: `guards` (optional) is a builder returning guards, each written `condition.$else(orElse)` (a non-enumerable method every condition carries beside `$and`/`$or`/`$not`; there is no `guard` function), whose conditions are `Rule` data built with the term operators (`line.quantity.$lte(line.stock)`, `lines.$length()`, `lines.$all(line => …)`, `a.$and(b)`/`a.$or(b)`/`a.$not()`), and `run` answers once every guard holds. It builds a `RulesDecision` (`kind: "rules"`, `run` stored as `otherwise`); an action with only `run` has no declared guard branches, but its opaque body now leaves `measures.constructions` undetermined and cannot pass strict checking. `id` is the action's name in reports. A free-form `Decision` object (`kind: "decision"`, an opaque `run`) is still accepted and is what makes arms `not measured`, but the docs no longer present it. `run` may be a `match(input => input.field.discriminant, { tag: handler })` (or `match(input => input.enumField, { value: handler })`, whose arms are the enum's values; `composeForWay` in `generate` then moves the enum position itself rather than the field holding a discriminant) — `match` takes the selected discriminant's literal union as its `Tag` type parameter and types `cases` as exactly those keys, so a missing or unknown case fails to compile; `implement` still refuses at run time a match whose selector passes through a field that may be left out (`match in … selects $.配送.方法, which may be left out at $.配送`: the match has no case for an absent value, and the term type cannot see the optional, so it compiled and then threw `No case of … for undefined` in `perform`; absence is a case of a sum instead), a match whose selector is neither an enum field nor a sum field's discriminant (a plain string field makes `Tag` `string`) or whose cases are not exactly that sum's cases, since the arms measure only sees the keys written. A guard's `orElse` is an ordinary result case — business rejections are never exceptions or a Result wrapper, following Souther — so preconditions such as an empty or already confirmed cart stay input cases that answer a rejection. `runTraced` also returns the arms taken, every comparison evaluated (with the scope it read), and the way through the guards; `comparisonsReached` gives the comparisons synchronously for `generate`. `action` infers its types from the case it is written for only (`NoInfer`). `implement`'s options are `NoInfer` as a whole, and so is `B` in its return type (`Implementation<NoInfer<B>>`): `B` must come from the definition alone. Without the latter, an `implement(...)` written inline inside `spec` took `B` from the specification's contextual return type (still `AnyBehavior` while `spec` infers its own `B`), and the literals in its `action` widened. `Tags`/`VariantOf` match `VariantsSchema<any, …>` — a literal discriminant is not assignable to `VariantsSchema<string, …>`, and that mismatch once made `Tags` `never` for every sum and silently disabled type-checking of `cases`.

A behavior may declare `ensures: clause => [clause.when(name, cases, (input, value) => rule), clause.always(name, …)]`, relating the input to the answer (a clause must name both roots). It is held wherever an answer is written or produced: implementation answers throw `SpecificationError`, answered example rows and conformance-subject answers become failures. A conjunct comparing the input with a constant (or two inputs) draws an `ensures` border, met by any answered row writing the value. Clause names are distinct within a behavior (`behavior` throws on a repeated one). `report.ensures` (`src/ensures.ts`) classifies every conjunct of every rule the way Souther does — `derivable` (numeric, decimal or temporal terms), `exact match` (`==`/`!=` over strings, booleans, literals, enums or discriminants), `always holds`/`never holds` (a rule that settles without the answer: constants, or two sides whose terms cancel, a term compared with itself, `x + y` with `y + x`, or `x - x` with a constant, read through `differenceOf`), `runtime only` (everything else, including `all`/`any`/`or`/`not`) — and lists the result cases no clause names (`unstated`, empty when no clause is declared or one is written with `always`). What a caller may assume after matching a case has nothing to seed in Chisel: the expression-model checker now verifies supported constructions and postconditions in `src/proof.ts`, every stage's answers are already held to its clauses at run time, and a composition measures no arms or ways of its own.

`requires: { name: dependency(outputSchema) | dependency(inputSchema, outputSchema) }` (`src/dependency.ts`) declares injected dependencies. Decisions and rules handlers receive the resolved dependencies as a second argument (`BehaviorDeps<B>`). An action's `guards` builder also gets a second argument, a term over the value dependencies (`ValueDepsOf`, function dependencies left out) rooted at `DEPS` (`"#deps"`); guards are evaluated against `withDeps(input, deps)`, i.e. the input with the dependency values under `#deps` (carried into `all`/`any` elements too), so a comparison reached records them. For measurement `guardScope` adds a `#deps` field of the value dependencies' output schemas to the case's schema, so borders, unread comparisons and feasibility read a dependency like a field; a border between a position and a dependency is named `deps.<name> − @case.<field>`, and `generate` composes it by moving the position against the stand-in the origin row writes with `with` (threaded through `comparisonsReached`/`traceSync`/`compose`). Rows stand in for value dependencies with `with` (`generate` gives every row it offers, including a row for an uncovered input case, a `with` holding the placeholder of each value dependency's output under what its origin row writes, as Souther writes `with` from the first generate; function dependencies get none, since a fake stands in for them), and a specification's `fakes: [fake(behavior, name, [[input, answer], ...], { otherwise })]` stands in for function dependencies. A row lacking a stand-in, a `with` value not of the dependency's type, and a fake miss are row failures; malformed, duplicated or dead fake rows are `fakeIssues` and the table stands in for nothing. A function dependency may also be declared as another behavior — `dependency(checkStock)` or, to bring its recorded rows too, `dependency(checkStockExamples)` — taking that behavior's input and answering its result (effects are not part of the answer). Its `ensures` are then read against every fake row (a row that breaks one is a `fakeIssue`), and a fake row asked what a recorded row asks but answering differently is a `fakeWarning`, which does not affect adequacy. A function a caller supplies (`Supplied`/`SuppliedDeps`, what `perform` and `runTraced` take) may answer a promise: `interpret` in `src/model.ts` reads the expression with a generator that yields only a call's pending answer, so a model whose calls answer values runs synchronously (as `traceSync` and the proofs need) and one whose call answers a promise is resumed by `resume` once it settles, the evaluation then answering a promise that `runTraced` awaits; `invokeDependency` checks the settled answer against the contract. Handlers keep `Resolved`/`BehaviorDeps`, typed as answering values: `answeringValues` in `src/behavior.ts` hands them each function dependency wrapped to throw `SpecificationError` on a promise answer, called on the supplied object (`Reflect.apply`, so a class instance's method and its `this` still work).

`disregards: { <case>: r => [r.field, ...], $default: r => [...] }` names, per input case, fields the answer does not turn on (`r => [r]` is the whole case), so behaviors can share one record model as their input. `behavior()` evaluates the builders once into `Behavior.disregards` (`Record<tag, string[][]>`, the key paths; `$default` is expanded into every unwritten case there, and a `$default` path no case it covers declares throws; `reachesPath` walks through a nested sum when any of its cases declares the rest, unlike `schemaAtPath`, which stops at a sum for `match`); `Disregards` is one mapped type over `Tags | "$default"` because an intersection with a separate `$default` member made its `r` a union inside the `behavior(...)` call. `measuredPositionsOf` in `src/specification.ts` drops the positions under a disregarded path, matched by `Position.segments` (the path as `["@case", ".key", "[]", ...]`, since a key may hold `.`; `isUnder` drops the `?` and nested `@case` markers after the input case, which a term steps through without naming), from `check`'s partitions and its `ensures` borders (matched by the border's `segments`, the way its invariant borders are dropped), and from the rows `generate` offers for classes and invariant borders only (a disregarded position a guard divides stays, stripped of its type classes and invariant borders, so the guard's classes still attach to it): input coverage, guard partitions/borders (`guardPartitionsOf`, `guardBordersOf`), arms, ways and `modelIssues` still read the whole input. `check` holds the claim (`disregardBroken`): for an answered row that passed, the disregarded positions under its case (a guard dividing one does not exempt it, since its type classes and invariant borders were still dropped) are moved, one `instancesIn` at a time (each array element and record entry the row holds is its own instance, named like `@case.lines[1].flag` or `@case.owners{"a"}`, and an empty container stands in with the one element or entry coverage would write), through every combination of their other classes (`place`) and of the owed invariant border points the row does not already meet (`write` with the point's witness, labelled `IN (> 0)` and so on), fewest moved first, skipping a combination the input cannot hold (one where a placed or unmoved position no longer classifies as chosen, or the input refuses it; an unmoved position another move leaves no longer held, such as a field of an optional left out, of a sum case left, or of an element cut off, is not counted as changed), and the model is rerun; the first changed answer or throw is one ordinary `failures` entry per row. Over the candidates limit (4096 raw candidates), or over the combinations limit (255 combinations the input can hold), the row is not tried; both are `check`'s `CheckOptions.disregards` (`chisel check --disregard-candidates` / `--disregard-combinations`), defaulting to `DISREGARD_CANDIDATE_LIMIT` / `DISREGARD_COMBINATION_LIMIT` and refused with `SpecificationError` unless a positive safe integer (`NaN` would compare as within every limit), since how far to go is the caller's policy, as Souther passes its budgets in and becomes an `incompleteness` entry of kind `disregards not checked`, which makes the verdict `undetermined` (the CLI prints it apart from rows it could not run). A composition takes its first stage's `disregards`. `implement`'s `cases` may carry `$default` (`CasesWithDefault`), which `casesWithoutDefault` hands, as one decision object, to every case not written, refusing it when every case is, and whose `match` is held to every case the selected sum has in any input case it decides, since `r` is typed as their union; `measureArms`/`measureRules` group decisions by identity (`decisionsWithCases`) so a shared decision's arms and ways are listed once, with feasibility read across every case it decides. An input case named `$default` is refused by `behavior()`.

3. **`src/specification.ts`** — the example/adequacy layer. `examples(behavior, { name: { given, with?, expect } })` builds a typed table of rows keyed by row name (duplicate names fail to compile; `Object.entries` order, so integer-like names come first), and `example(behavior, { given, expect })` types a single row built outside a table; where `expect` is either a concrete `Execution` or `todo(reason)`. An `Execution`'s `result` may instead be `caseOf(tag)` (`CaseOnly`, `src/behavior.ts`, marked with a `Symbol.for` property so a copy from the CLI's module graph is recognised by `isCaseOnly`), Souther's bare case name: `runAndCompare` (through `answers`) and `test` compare the answer by `tagOf` and the effects in full, `check` takes the tag as the row's result case (specified, verified when the run answers it), checks it is one of `variantTags` instead of parsing it, and holds no `ensures` against it, and `fakeWarningsOf` compares a fake answer with such a recorded row by case. `todo(reason)` is the one marker for anything not decided yet: an answer in `expect` (the row still runs, so it counts as executed but never as verified), a case in `cases` (running it throws `TodoDecision`; a row that reaches one is not a failure but a `row not run` in `incompleteness`, and a composition lists its stages' open cases as `<stage>: <case>` in `pendingDecisions`), or a control in `controls`; the report names it by where it sits (`unanswered`, `pendingDecisions`, `controlGaps`). `spec(name, { examples, implementation? })` ties an example set to an (optional) implementation. `check` is the core analyzer: it walks every example, tracks input/result/effect variant coverage, collects unanswered rows, pending decisions and control gaps, and — if an implementation is present — actually runs it against each example (`perform`) and deep-equal-compares the outcome, reporting mismatches as `failures`. The run-and-compare logic is factored into the private `runAndCompare` helper, shared with `test` below. The result is an `AdequacyReport`; `adequate` is exactly `verdict === "satisfied"`, which additionally requires feasible pairs and verified constructions. The report also carries `evidence` graded the way Souther grades it (an input case is `specified`/`executed`/`verified`, a result case `specified`/`observed`/`verified`; a row whose answer is owed still runs, so it can execute and observe but never specify), `measures.arms` (`not applicable` without an implementation, otherwise `not measured` with a `notRead` list of decision ids — a `Decision.run` closure is opaque, so its branches are never read), and a `verdict`: `not_satisfied` when a gap was found, `undetermined` when none was found but the arms could not be measured, `satisfied` only when nothing is left unmeasured. `--strict` exits 1 exactly when `adequate` is false; unreadable measures and unproved constructions now fail strict checking. `generate` emits `todo()` rows (with schema-derived placeholders) for every uncovered input variant and then for every class no existing or generated row stands in, moving only the position that class belongs to — this is what backs `chisel generate`. A row the input refuses because it breaks an invariant relating finite positions is chosen again by `keepingInvariants`: the finite positions it moved from its origin stay, the others such invariants connect are chosen by the same search, preferring the values the row holds, and the row is offered when the input takes it (a choice that would take another case of a sum field is not made); one it still refuses because it breaks an invariant ordering two or more integer or number positions is kept by `keepingOrderings`, which moves a part weighed by one that the row did not move to the nearest value keeping it that its own bounds admit (`nearestKeeping`: `正 < 記録` with `正` moved to 1 writes `記録 = 2`, or, for a `number()` at most 1.5, `1.25`, as a number has no step); `GenerationOptions.feasibility.combinations` (`chisel generate --feasibility-combinations`) bounds that search as `CheckOptions` does. Rows whose answer is owed count as already asking, so they are not generated again. `test` is a separate, narrower check: it runs *only* the answered examples against an arbitrary async subject function (e.g. a real controller/service) and returns `{ failures, skipped }`, `skipped` naming each row left out because its answer is still `todo`, so a test decides whether an open answer may pass, keeping "does the model make sense" (adequacy) separate from "does infrastructure code conform to the model" (conformance).

4. **`src/cli.ts`** — thin politty wrapper over the above. Loads a spec file's module via `tsImport` (so `.ts` files run without a build step), discovers exported `Behavior`s and `Specification`s by shape (`isBehavior`/`isSpecification`), synthesizes an empty specification for any behavior that's exported but not wrapped in `spec` yet, and backs the `check` subcommand (prints `AdequacyReport`s) and the `generate` subcommand (prints ready-to-paste `example(...)` rows via `formatTypeScriptValue` from `src/codegen.ts`).

`src/partition.ts` derives the positions of a behavior's input from its schema, Souther-style: every field under each input variant is a position named by a path such as `@商品あり.クーポン` (`@` narrows to a sum case, `[]` steps into array elements, `?` into what an optional holds). `optional` divides into `なし`/`あり`, `boolean` into `true`/`false`, `enum` into its values, and a sum field into its cases; objects, array elements and optional payloads are taken apart recursively; everything else is `not-derivable` — the model draws no line through it, which is a fact about the model and never a gap. Record values are a position under `{}`. A `DividedPosition` can `classify` a given value and `place` a class into one (forcing the enclosing sum cases and writing an array element where needed); every position can `write` a coordinate (a length written into an empty array or record fills it with the element's or value's placeholder, since there is no element to repeat), which is how `generate` composes rows (these coverage moves touch the first array element and every record entry; `instancesIn(given)` gives one instance per element and entry, built from the same `Focus` steps by `descend`, for the disregards check) — starting from the first answered row that reaches the position and moving only that position, falling back to placeholders. An array or record with no invariant of its own is not a position — only its elements are — but `positionsOf(input, { containers: true })` (used by `guardBordersOf`) keeps it as a `not-derivable` position so a guard on its `length` can still be composed by resizing it; a guard point `generate` still cannot compose is named in `notComposed` rather than dropped.

Invariants feed the same analysis (`src/border.ts`). An `eq`/`ne` rule on a boolean or on a sum field's discriminant `excluded`s the classes it refuses (counted as declared minus excluded). A rule comparing one coordinate — a value, or the `length` of a string/array/record — with a constant draws a `Border` on that position (an object invariant naming one field draws it on the field; one relating two fields draws none on either field, and a position with borders but no classes is `bounded`; an ordering of two numeric or temporal positions in an invariant of an input case or of the input sum is drawn on their difference instead by `invariantPairBordersOf` in `src/guard-borders.ts` (for the input sum's and the case's invariants and those of every object a field holds, `objectFramesIn`, which like `jointInvariantsOf` does not descend optionals, arrays, records or sum fields; a nested object's border reads its coordinate from the object its frame stands at, a point is excluded by another invariant only when both compare the same two positions by the same measures (`length($.a) − length($.b)` and `length(trim($.a)) − length($.b)` are different differences), one whose sides cancel, `$.x <= $.x`, draws no border, and one that then never holds, `$.x < $.x` or `$.x - $.x != 0` against a decimal, is reported in `modelIssues` by `invariantContradictionsOf` unless a field it reads may be left out (`mayBeLeftOut`), since a comparison with an absent side holds; nor are a pair's borders that leave no value reported when one of the two may be left out), through the same `between` a guard's pair border uses but read as an invariant, so its `ON`/`IN` points are owed and `OFF`/`OUT` excluded, as Souther draws an input relation's border; `check` meets a point by any answered row of the case writing the value, as an ensures border is met, and `generate` offers a row at each point no row stands at). A border has the four domain-testing points: `ON`/`IN` are owed a row, `OFF`/`OUT` are `excluded` because nothing outside an invariant can be constructed, and `IN` is excluded where the rules leave that side one value wide. Whether a neighbouring value exists depends on the carrier: `int` and lengths step by 1, `decimal(scale)` by one unit of its last digit (`decimalCarrier`, whose `snap` moves a bound written off that grid onto it, `>= 0.004` in cents drawing the border of `>= 0.01`; an equality with a value off it settles without a row, `$ne(0.005)` in cents always holding and `$eq` never, so it is refused wherever a rule is written: `refine` (and the shorthands) throw `refine compares $.合計 with 0.005, which no decimal(2) holds: $.合計 != 0.005` through `offGridEquality` in `src/schema.ts`, which reads each term's schema and each `all`/`any` element through its array, `behavior` throws `Ensures <name> compares value.合計 with …` through the same walk over `scopesOf` in `src/ensures.ts`, and `implement` throws `guard in <id> compares …` through `offGridEqualityIn` in `src/guard-borders.ts`, which walks guards with `thresholdsIn` since their terms reach `#deps`; all three share `holdsNoDecimal`, so `snap` only ever moves an ordering; an expression of integers and decimals compared with a decimal is held on the grid of its finest decimal (`decimal(0)` included) less its constant, `$.甲 + $.乙 == 0.005` in cents refused, by `offGridExpression`, which `offGridEqualityIn` also runs over each guard), `instant`, `datetime` and `time` by 1ns and `date` by a day (`step` in `src/rule.ts` moves a placeholder the same way, since adding a nanosecond leaves a plain date unchanged); `time` has a `floor` and a `ceiling` (00:00 and 23:59:59.999999999, and its step stops at them rather than wrapping past midnight), so a point beyond either end is `no point`, and feasibility reads the ceiling as an upper bound too; `number` and `string` have no step, so their `OFF` point is `not named` and a strict bound on them draws no border. A rule naming one value (`eq`/`ne` against a constant) has a point on each side of it and reports the role it has no point in as `no point`. A point one invariant owes is `excluded` when another invariant on the same measure refuses its value (`withoutRefusedPoints`), and a position whose invariants on one measure then owe no point at all admits nothing: it is reported in `modelIssues` (which makes `adequate` false) instead of as gaps. Lengths use `lengthCarrier`, whose `floor` (0) turns every point lying wholly below zero — an `OFF`/`ON` value under 0, or an `IN`/`OUT` run below an edge at or under 0 — into `no point`, for invariant and guard borders alike. Invariants written on a sum (the behavior's input sum or a sum field) are passed down to every case like object invariants, so a rule naming a field the cases share draws its border on that field under each case; a rule on the input sum's discriminant excludes the input cases it refuses (`excludedCases`), which then drop out of `report.input` (listed in its `excluded`), of the input evidence, and of `generate`.

Guards feed it too (`src/guard-borders.ts`). A guard comparing a position with a constant draws a border whose `OFF`/`OUT` points are owed (both sides can be constructed) unless the position's invariants refuse them, and its thresholds divide the position into interval classes merged with the invariant range; an interval the invariant range leaves empty is listed in `excluded` rather than dropped. A guard comparing two positions divides neither and draws its border on their difference (integers, numbers, lengths, two decimals as a bigint of units of the finer scale (`decimalUnitsCarrier`; composing moves the finer side, since a coarser one cannot hold every difference, and a decimal is compared with no other kind; where the input refuses the row that moves it, as when that side has a bound of its own, `generate` moves the other side of the same scale instead (`compose`'s `otherSide`), for a guard's and an input invariant's pair point alike), dates in days, or instants, datetimes and times in nanoseconds, a datetime read through UTC as an exact bigint; composing a time that would wrap past midnight moves the other side instead). An `eq`/`ne` between two positions draws no border and is not an unread comparison: following Souther, an equality between two positions puts a whole arm on each side of the line, so the arms and rules measures cover it; `between` returns no border for `==`/`!=` on purpose. A guard border point is met only by a row whose run reached that comparison, not by one that merely writes the value, and only by a row of the input case the border was drawn under (`GuardBorder.origin.tag`), since a `$default` decision shares one comparison object across the cases it decides. The analysis keeps each rendered path beside its segments (`Frame`, `GuardPartition` and `GuardBorder` carry `segments`), and finds positions and matches partitions to them by segments, never by the rendered path, since a key holding `.` renders the same as the nested path it spells. Comparisons Chisel cannot read (e.g. two strings ordered against each other, or an enum ordered against a value, since its values order by their text rather than as they were named) are listed under `measures.comparisons`, which makes the verdict `undetermined`. `measures.arms` covers each guard's `holds`/`else` and each `match` case; `measures.rules` (`src/ways.ts`) covers each way through the guards, enumerated depth-first with short-circuiting (`eachWayOf` yields them one at a time; `waysOf` lists them all). How a decision is measured is planned once per decision (`plansOf` in `src/specification.ts`, read by `measureRules`, `measureArms` and `generate`): where every position its guards and `match` read is a boolean, an enum or a sum's discriminant (an optional one only where the field itself may be left out, whose absence is one more value; `#deps`, `all`/`any`, lengths and anything under an optional container make it ineligible) and the product of their domains, with the input's own discriminant, is within `CheckOptions.feasibility.combinations`, `finiteReach` in `src/feasibility.ts` adds every finite position an invariant reading only finite positions connects to them, and tries every combination that keeps those invariants (`fieldInvariants`: those of the case, of the input sum, of each object and field and of what an optional holds), follows the guards on it with `traceFinite` (the guards' own `holds`, no handler run and no parse, so a placeholder another invariant refuses cannot drop a combination), and lists only the ways some combination takes, sorted into `waysOf`'s order (`inWayOrder`), each `met`, `answer owed` or `gap`; an arm none takes is `no row owed` (`どの値の組もこの分岐を通らない`), and a way none takes is not listed at all. Otherwise at most `CheckOptions.feasibility.ways` ways (`WAY_LIMIT` = 10000, `chisel check --feasibility-ways`) are listed and settled as before; a decision with more is reported in `notRead` like an opaque one, which leaves the verdict `undetermined`, and `reachOf` leaves a guard border point `undecided` (`道筋が上限のN本を超える`) past the same limit rather than build them all. A way (and an arm, through the ways that pass it) no row took is classified by `src/feasibility.ts`: comparisons with constants are gathered per coordinate together with that position's invariants and settled on its carrier (a sum discriminant, boolean or enum on its finite domain, less the values its invariants refuse, so the arm of a refused value is `no row owed` where the partition already counts it `excluded`), and a comparison between two positions is settled on their intervals when each position takes part in comparisons with only one other position; the comparisons of one pair of integer or number positions (the steps of a way and a point placed on them) are settled together on their difference (`differenceCarrierOf`; two decimals or temporal values differ in units the steps do not carry, so more than one comparison of such a pair is left unsettled). Both are one `Form` in `feasibilityOf`: a pair is the form `a − b`, a comparison of an expression (`readableFormOf`, which leaves unread one holding a field that may be left out, since a comparison with it absent holds) is `differenceOf(rule)`, and a point of an expression border is placed as `{ form }`; forms are made canonical (parts merged and sorted, the first coefficient made positive), so `甲 + 2 <= 乙` and `乙 − 2 <= 甲` constrain one form, and a contradiction among a form's constraints is `no row owed`; a pair no other form shares (such as `x − y >= 5`, which no relation carries) and a form of more than a pair none of whose parts is part of another form are settled on the range their parts' own intervals give them (`rangeOf`, an integer's exclusive edge stepped in first), on integers only when every coefficient is ±1 (or, with no part bounded, when one is), so a contradiction with that range is `no row owed`; it is left `undecided` otherwise. An input invariant ordering two or more integer or number positions never left out, or comparing their expression with a constant (`numericFormOf`), is added to a form the way already constrains, and only to such a form, since a form of its own sharing the way's positions would leave settled forms undecided: a guard `x <= y` under an invariant `x <= y` owes no row at its `OFF`/`OUT` points. A contradiction makes it `no row owed`; an `all`/`any` condition sharing a value with another step, or anything left unsettled, makes it `undecided`, which turns the verdict `undetermined` instead of `not_satisfied`. Invariants relating two or more finite positions are read too (`jointInvariantsOf`): each invariant written on the case object, on an object one of its fields holds (with that field's path as its prefix; optionals, arrays, records and sum fields are not descended), or on the input sum (`feasibilityScope` in `src/guard-borders.ts` adds the sum's invariants to the case and declares its discriminant as an `enum` of the one case, so a rule naming it reads as that value) whose every comparison is `==`/`!=` of a finite position (or what `$lowercase()` and the other transforms read of it) with a constant or with another finite position, combined with `and`/`or`/`not`; an invariant with any other comparison is left unread, as before. `jointAssignments` takes the finite positions a way constrains, adds every position such an invariant connects to them, and tries the combinations of their domains (each narrowed by the way's own constraints) that keep every connected invariant; none makes the way `no row owed`, and more combinations than the caller's limit (`CheckOptions.feasibility.combinations`, `chisel check --feasibility-combinations`, `FEASIBILITY_COMBINATION_LIMIT` = 4096 by default, refused with `SpecificationError` unless a positive safe integer through the same `positiveLimit` as the disregards limits) makes it `undecided` (`不変条件とあわせて調べる値の組が上限のN通りを超える`). A way no such invariant reaches is settled exactly as before. The same search (`refusedJointly`) excludes a class of a boolean, an enum or a sum field directly under a case that no kept combination gives the position (`withJointExclusions` in `measuredPositionsOf`, shared by `check` and `generate`; past the limit it is not excluded). `generate` skips infeasible ways, and the CLI counts both states per reason instead of listing them. A feasible way no row took is composed by `composeForWay` when it ends in a `match` (moving the matched position of a row that reaches it), and otherwise, only when `generate` is given `GenerationOptions.ways` (`chisel generate --ways`, off by default since every way owes its own row), by `composeFromWitnesses` when every step is a `match` or an `==`/`!=` comparison of a finite position (a boolean, an enum or a sum's discriminant) with a constant: `witnessesOf` in `src/feasibility.ts` yields, through `jointAssignments`, the combinations of values for the way's finite positions and the positions the invariants relating finite positions connect to them that keep those invariants (the input's own discriminant, which the case object does not declare, takes only the case the way is composed under and is not placed), and `generate` places each combination in turn into every answered row of the case, then its placeholder, keeping the first that the input takes and that takes the way. Where `plansOf` measures the decision by its combinations, `generate` walks only the ways they take, and with `ways` writes each from the combination that takes it (`composeFromReach`; a field left out is placed as its optional's `なし` class); past the limit on ways it names the decision once (`<id>: 道筋が上限のN本を超えるため組み立てない`) instead of its ways. Either row is offered only when it takes the way; a way with an ordering, a length, `all`/`any`, a dependency, or a field the cases of a sum field share (`schemaAtPath` stops at the sum, so `witnessesOf` finds no domain for it) is still named in `notComposed`. A guard border point no row met is settled the same way: its region (`BorderPoint.region`) is placed on the compared coordinate and checked together with the steps of each way before that comparison (`reachOf`; a comparison between two positions places the point on their difference, and comparisons inside `all`/`any` are not placed), so a point only reachable with values outside it — the points of `x >= 5` behind `x >= 10` in an `and`, or the `IN (> 0)` point of `x >= y` behind a guard `x <= y`, which Souther refutes as a point the rules leave no value at — is `no row owed` and `generate` offers no row there.

`src/composition.ts` provides `compose(name, [implementations...])` (Souther's `>->`): it takes two or more stage implementations and returns `[composition, implementation]`. Stages are folded left to right; each join is an ordinary `Behavior` whose input is the first stage's and whose result is the cases the earlier stages answer that the next stage's input does not take (they *depart*) plus that stage's result cases, carrying `pair` and `departed` (also in the type, so a departed case never reaches a later stage). The composition keeps its stage behaviors as `stages`. All result/input sums must share one discriminant, a tag that would both depart and be answered by a later stage is refused, a case flowing on to the next stage may not carry a field that stage's input does not declare (compared by keys at every depth through objects, array elements, optionals on either side, record values — an answered object's fields are compared with the record value the next stage takes — and nested sums, where a case the next stage does not declare, or a discriminant it names differently, is refused too; an answered sum taken as a plain object must have its discriminant and every case's fields declared there, and an answered object taken as a sum is compared with the case its literal discriminant names. The other direction is held too: a field the next stage requires (not `optional`) that the answered case leaves out or answers only as optional, including the discriminant of a sum the next stage takes, is refused as `<first> does not always answer <path>, which <second> requires`; a record the next stage takes requires no key, and an enclosing sum's discriminant always travels with the value, so neither counts. It is refused with its path such as `@有効.明細[].単価` or `@有効.支払@カード`; a sum's discriminant that the answered case declares for itself is not counted, and declaring the same shape twice is fine. Types are held too, on the rule that every value the answered schema allows must be one the taken schema takes: a leaf of another type, a container of another kind (a record taken as an object may carry any key, so it is refused), a literal of another value, a string taken as one literal and a number taken as an integer are refused as `<first> answers <path> as <kind>, which <second> takes as <kind>`, while an integer taken as a number, and a decimal taken as a decimal of at least its scale, is accepted (a decimal taken as a number or an integer, or of a larger scale, is refused as `decimal(3)`), and a literal is judged by parsing its value with the taken schema and an enum by parsing each of its values (so it goes into a string or a wider enum, not a narrower one) (so `literal(Infinity)` taken as a number, or a literal a taken invariant refuses, is refused); a sum's tag is compared as a literal with the discriminant field the next stage declares (on a plain object or on the case object itself), whatever type the answered case declares for its own discriminant, since the value always carries the tag, an answered sum taken as a record has each tag and field compared with the record value, and an answered object taken as a sum must name its case with a string literal or an enum, each of whose values is then compared as that case. Composition declaration otherwise leaves invariants to run time; `verify` additionally proves forwarded schema inclusion using structural and numeric contracts or exhaustive finite domains, and leaves an unproved handoff undetermined), effects and `requires` are united, and a composition carries no `ensures`. The returned implementation nests binary `pipeline`s; `runTraced` runs the first half and hands the answer to the second only when its tag is on the main line and the second takes it, concatenating effects. A composition's arms and rules measures are `not applicable`, and guard-derived borders/classes/unread comparisons are empty because its `cases` is. `external(behavior, reason)` (in `src/behavior.ts`) is an implementation Chisel never runs — distinct from `todo`, nothing is owed: `perform` throws on it, and `check`, finding one in an implementation (or any stage of it), records every row as `row not run` in `incompleteness` instead of running it, reports its arms/rules as `not measured`, and makes the verdict `undetermined`. `generate` prints, for a behavior whose specification has no implementation, an `implement` scaffold with every case and control `todo`.

`src/beside.ts` holds Souther's E1938 (every border is told from the lines beside it): a guard border over two or more integer or number positions carries a `form` (`BorderForm`, its parts with their weights, `valueOf` and `write`), and once every point it owes is met (`no row owed` aside) `check` reads the rows that reached the comparison into `BorderCoverage.beside`: `linesBeside` moves each weight, in the order of the parts' paths, by +1 then −1, reduces each line by the common divisor and drops repeats, `lineTheRowsAllow` keeps the first on which a cut (the furthest kept row) keeps every kept row and refuses every refused one strictly past it, and the border is `not told` (which makes `adequate` false), `told`, or `undecided` when no row that reached it was kept. A `not told` border names `input` as Souther's `partingAt` does: `partingsOf` steps from each row (kept rows first) along a direction the border weighs to nothing and the line does not (`alongTheBorder`, `{i: w_j, j: −w_i}` for the first such pair), within two steps of where the line's cut is crossed, keeping the inputs the line answers differently at; `besideOf` in `src/specification.ts` writes each through the parts' `write` onto the row it came from, keeps those the input takes and that still reach the comparison (`comparisonsReached`), and picks one the decision's other guards also keep, then the fewest steps. `reached` items carry the row's `given` and stand-ins for this. `generate` reads the same from the rows that reach the comparison once each point those rows meet leaves none owed, and offers a row at the input (`<path> 隣の線 (<line>)`) with the stand-ins of the row it stepped from, answered or not (`besideOf`'s `deps`, since an earlier guard may read them), or names it in `notComposed` when `besideOf` found none. Invariant and ensures borders and borders with a stand-in are not read.

`src/report-json.ts` projects `AdequacyReport`s into the `check --json` document (`reportDocument`): it adds `sources`/`source`, an `obligationId` to every border point, arm and way (disambiguated with `#n` when two read alike), and `weakening` to every measure that is `partial` or `unavailable` for want of something it could not read. Those JSON-only fields are kept out of the in-memory report on purpose; `schema/report.schema.json` is the closed schema of the document, and `test/cli.test.ts` validates real documents against it with a small validator (`test/support/json-schema.ts`) — adding a field to the report means adding it there.

`src/codegen.ts` is a small, standalone pretty-printer from runtime values back to TypeScript literal syntax (including `Temporal.Instant.from(...)`, `Temporal.PlainDate.from(...)` and the other temporal types), used only to render generated example placeholders: keys are bare where they are identifiers (Unicode identifiers included), every multi-line object/array item ends with a comma, and `undefined` is written as `undefined` (a row for an optional array element or record value holds one to stand in the absent class, so dropping it would make the row miss that class). `chisel generate` prints, for a behavior it had to synthesize a specification for, the `import ... from "chisel"` line (once per run) plus `examples(...)` and `spec(...)` blocks; for a real specification it prints only the rows, each ending with `,`.

## Key invariants to preserve when editing

- `variants`'s `parse` merges the discriminant tag back into the parsed value (`{ [discriminant]: tag, ...result.value }`) — variant object schemas do not need to declare the discriminant field themselves.
- Coverage/adequacy analysis (`check`, `generate`) depends entirely on `VariantsSchema.variantTags` and `tagOf`; if you add a new schema kind that can appear as a behavior's `input`/`effects`, it must stay a `VariantsSchema` or the coverage model breaks.
- `perform` and `check`'s implementation check both re-validate input/result/effects through the schema, even though the example row was presumably already schema-valid — don't remove this, it's what catches implementation code that returns malformed data.
- Stale examples are meant to fail to compile when the data/behavior model changes (see `examples/progressive-demo/type-break/`) — this is a deliberate correctness mechanism, not something to work around with looser types.
- `object()`'s `parse` refuses a key its shape does not declare instead of dropping it, so a model that answers with a stray field (say, spread from its input) fails `check` the way it fails `test`, rather than having the field vanish before the comparison.
- `object()`'s `parse`/`placeholder` drop a field entirely when its value is `undefined` (this is how `optional()` fields disappear instead of being written as `undefined`). Keep that: `check`/`test` compare examples with `deepEqual` (`src/equal.ts`, Node's `isDeepStrictEqual` without the Node module, telling built-ins by their internal slots as Node does, except that it compares Temporal values by what they hold and takes objects of different prototypes as different; fake rows reach it as written, before any schema reads them), which treats `{ note: undefined }` and `{}` as different — writing an explicit `undefined` key would make schema-normalized values fail to match hand-written examples that simply omit the field.

It's the reference example for how the four stages are meant to compose in practice — read `examples/progressive-demo/README.md` and the stage files in order before changing the demo or the underlying API surface it exercises.


## JSON and external conformance

`src/codec.ts` exports `decode(schema, parsedJson)` and `encode(schema, domainValue)`, both returning `ValidationResult`. Conversion follows schema metadata; decimals and Temporal types use strings, and the existing schema parser checks invariants and extra keys. Do not coerce decimal JSON numbers or silently replace absent array/record values with null. `parse` itself still takes domain values.

`evaluate(exampleSet, rowName, subject)` runs one recorded example and returns a `RowEvaluation` (`passed`, `failed`, or `skipped`); missing names throw. `test` loops over the same private `evaluateRow`, preserving `{ failures, skipped }`. Both validate input, expectations and actual result/effects, with `ensures` held after shape validation. Production setup belongs to the caller, not `with` or `fakes`.

The CLI accepts `--behavior` on `check`, `generate` and `run`, matching the declared name. `run` can load an exported implementation without a separately exported behavior, selects exactly one distinct implementation, refuses dependencies, decodes `--input`, performs once and encodes the execution. The other commands retain their behavior/spec export discovery. `docs/souther-comparison.html` records the comparison against a pinned Souther commit.


## Inspectable models and strict guarantees

Use `model(id, builder)` from `src/model.ts` for certified implementations. The builder produces an immutable expression tree containing terms, `choose`, `construct`, `arithmetic`, `quotient`, `concat`, and the temporal `plus`, `minus` and `between` (`src/temporal.ts`; `interval.ts` measures dates, date-times and instants as nanoseconds since 1970-01-01, so units of fixed length are proved like integers); runtime evaluation never calls a model callback. `ways.ts` enumerates all contributing branch combinations. `proof.ts` proves finite domains exhaustively and supported symbolic constructions conservatively; `interval.ts` uses exact Rational bounds. An unproved result stays `undetermined`, and both `verify` and `check --strict` fail. Legacy callbacks remain executable but never establish universal construction safety.

`data.ts` provides nominal named objects and validated immutable construction. Named `construct` nodes require `implement(..., { constructs: [...] })`. `exact.ts` provides Rational and signed-64-bit bounds; `int64()` and `rational()` integrate with schema, carriers, codecs and code generation. String parsing is NFC with Unicode scalar length and ordering. `domain.ts` shares bounded candidate generation and exhaustive-domain evidence; `pairs.ts` classifies feasible, impossible and undecided pair obligations, with no inference of impossibility from unsuccessful sampling.

The CLI adds `verify`; all executable CLI commands use `isolated.ts` workers with time, heap and output limits; `runIsolated` is exported from the `chisel/isolated` entry, not from `src/index.ts`, which reaches no `node:` module (held by `test/web-apis.test.ts`). In-process APIs retain their normal execution context. `npm run build` compiles and verifies `examples/verified.spec.ts`. `docs/editor-task.json` is a problem matcher example; no standalone LSP is installed. The JSON report's additive `measures.pairs` and `measures.constructions` are part of schema version 2.

### Contract proofs across dependencies and collections

`call(deps.name, argument)` in `src/model.ts` invokes a declared function dependency. Model builders receive terms for both value and function dependencies. `prepareExpression` in `src/proof.ts` proves call arguments, replaces each occurrence with a fresh result term, and adds supported unconditional dependency postconditions to the proof scope. `bind` and exhaustive `matchValue` expose result fields and narrow variant tags; matching case-scoped postconditions then supply proof facts. Calls are independent, never evaluated during verification, and never universally certified from fake tables. `invokeDependency` validates inputs, outputs, and applicable postconditions at runtime and snapshots both boundary values, including Decimal coefficients. Model inputs and value dependencies are also snapshotted; unsupported host object instances are rejected rather than shared. Raw call results are expressions; their bound values provide field and guard terms.

`scopeFacts` carries matching quantified invariants from nonoptional input objects into proofs; substitution preserves bound quantifier names and resolves free captures. Structural inclusion recursively checks collection elements and object fields. `map` proves its body against an explicit output-element schema; `fold` proves its initial value and every update against an explicit accumulator schema. Nested bodies share the proof-path budget and iterations share the runtime evaluation budget. Local references cannot escape their binding, binding declarations cannot be reused, and top-level input names starting with `#local:` are reserved. Local and repeated branch coverage remains unmeasured, so those models cannot pass strict checking solely from a construction proof. Branch-free collections remain eligible for strict checking. Recursive and general higher-order proofs, array-length relations, and fold postconditions beyond the declared accumulator contract remain unsupported. Whole-input terms retain the original input without internal dependency or local bindings; `#deps` is reserved on input variants only when dependencies are declared.

## Invariants a world keeps

`src/world.ts` holds `world(name, { state, initial, operations, invariants, transitions })`, `invariant(name, state => condition)`, `transition(name, (before, after) => condition)` or `transition(name, { each, by }, (before, after) => condition)` and `explore(world, { runs, steps, seed })`. An invariant is kept apart from the state's schema, which may admit states no operation reaches; `explore` checks only states reached from `initial`. A condition is a `Rule` (read by `holds` over the state, or over `{ before, after }` through `rootTerm`; `refusedBy` skips a step whose state `deepEqual`s the one before, as `[][P]_vars` does, and with `each` pairs the records at that dotted path by their `by` field or record keys through `recordsAt`, comparing keys by `deepEqual`, holding each changed pair and breaking on a state holding two records with one key); `world` refuses, through `pairable`, an `each` reaching no array or record of the state schema or a `by` the records do not declare or a model expression `interpret` evaluates to a boolean; `checks` tells them apart by `nodeOf`. An operation is `{ implementation, state }` (the state at an input and result field, the rest drawn by the sampler) or `{ implementation, input, next }` (a part of the world, its input built through `Draw`). `walk` runs one walk from a `choose(step)` that gives the operation and a random source, handing `input` and `next` (or `inputFor`) one `copyOf` the state per step, so a callback that changes it in place reaches neither the recorded `before` nor `initial`, and counts a step as `moved` by `deepEqual`; exploration records each step's draws as a `Plan` tape, and `shorten` drops plans from the last while a replay of the rest breaks the same invariant. The sampler draws each leaf from `domainOf` (bounds, borders, guard constants via `constantsOf`), integers also between those values, arrays and records at lengths their `integralBounds` allow up to `MAX_LENGTH` past the lower one; the random source is a seeded mulberry32. `explore` reports `undetermined` (with `reason`) when an operation never ran or was `pending` (an `external` implementation via `externalsIn`, or a `TodoDecision` it threw), counts `skipped` and `pending` per operation, draws a whole-world operation's input without its state field and takes its next state from the result's field by presence (`stateIn`, so an explicit `null` is parsed as the next state and only an absent field leaves the state as it was), and takes `runs` and `steps` through `positiveLimit` (both exported from `src/specification.ts`) and refuses a `seed` that is not an integer from 0 to 2^32 − 1, since mulberry32 reads only its 32 unsigned bits.
